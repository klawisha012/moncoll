# Набор тестов WAF

В этой директории находятся автоматические тесты для Web Application Firewall (WAF). Набор тестов разделен на несколько уровней (Unit, Integration, E2E и Load Testing) для баланса между скоростью выполнения, изоляцией и полной проверкой всей системы.

---

## Структура директории

```text
tests/
├── conftest.py             # Корневая конфигурация pytest (автоматически применяет маркеры)
├── requirements.txt        # Python-зависимости для тестирования
├── unit/                   # Юнит-тесты (внешние зависимости изолированы, быстрые, без I/O)
│   └── backend/            # Юнит-тесты бэкенда
├── integration/            # Интеграционные тесты (FastAPI роуты, база данных, моки внешних сервисов)
│   ├── backend/            # Интеграционные тесты бэкенда
│   └── test_dashboard_router.py
├── e2e/                    # End-to-End тесты (тестирование "черного ящика" на полном docker-окружении)
│   ├── auth/
│   ├── connections/
│   ├── crowdsec/
│   └── modsecurity/
└── loadtest/               # Нагрузочное тестирование с использованием k6
    ├── k6/                 # Скрипты для k6
    └── README.md           # Инструкции по запуску нагрузочных тестов
```

## 1. Подготовка окружения

Перед запуском тестов убедитесь, что установлены все необходимые зависимости. Мы рекомендуем использовать `uv` для быстрой работы с пакетами, но стандартный `pip` также поддерживается.

### Установка зависимостей

```bash
# Через uv (рекомендуется)
uv pip install -r tests/requirements.txt

# Или через pip
pip install -r tests/requirements.txt
```

---

## 2. Юнит-тесты (Unit Tests)

Юнит-тесты выполняются очень быстро, работают полностью в оперативной памяти и не требуют запущенных баз данных, docker-контейнеров или сетевых подключений. Все внешние вызовы (такие как DNS-разрешение, SMTP или API капчи) полностью изолированы с помощью моков.

### Запуск юнит-тестов

```bash
# Запуск всех юнит-тестов
pytest -m unit

# Альтернативный запуск по пути к директории
pytest tests/unit/ -v
```

---

## 3. Интеграционные тесты (Integration Tests)

Интеграционные тесты проверяют корректность работы API-эндпоинтов, переходов состояний и операций с базой данных. Для их работы требуется запущенный экземпляр **PostgreSQL**, на котором будут автоматически выполнены миграции базы данных и транзакционные проверки.

### Шаг 1: Запустите тестовую базу данных
Тестовую базу данных можно легко запустить в Docker. Мы подготовили специальный конфигурационный файл (`docker-compose.test.yml`), который пробрасывает PostgreSQL на порт `localhost:5432`, не мешая вашей основной базе данных для разработки.

```bash
docker compose -f docker-compose.yml -f docker-compose.test.yml up -d postgres
```

### Шаг 2: Запуск интеграционных тестов

```bash
# Запуск всех интеграционных тестов
pytest -m integration

# Альтернативный запуск по пути к директории
pytest tests/integration/ -v
```

### Настройка URL тестовой базы данных
По умолчанию интеграционные тесты подключаются к `postgresql+asyncpg://waf:waf@localhost:5432/waf_test`. Вы можете переопределить эту строку подключения с помощью переменной окружения `TEST_DATABASE_URL`:

```bash
# Для Linux/macOS
TEST_DATABASE_URL=postgresql+asyncpg://user:pass@host:port/db pytest -m integration

# Для Windows (PowerShell)
$env:TEST_DATABASE_URL="postgresql+asyncpg://user:pass@host:port/db"; pytest -m integration
```

> [!WARNING]
> Запуск интеграционных тестов автоматически вызывает `drop_all` и `create_all` для целевой тестовой базы данных. Убедитесь, что `TEST_DATABASE_URL` не указывает на рабочую (production) базу данных!

## 4. Сквозные тесты (End-to-End / E2E Tests)

E2E-тесты проверяют систему в сборе. Они выполняют реальные сценарии "черного ящика" через прокси-сервер Angie, ClickHouse, Centrifugo, Redis и бэкенд-процессы, запущенные в docker-контейнерах.

### Шаг 1: Запуск полного стека сервисов
Убедитесь, что локальный стек запущен и собран:

```bash
# Генерация свежих файлов окружения, если вы этого еще не сделали
./scripts/generate-env.sh

# Запуск всего стека
docker compose up -d --build
```

### Шаг 2: Запуск E2E-тестов

```bash
# Запуск всех E2E-тестов
pytest -m e2e

# Альтернативный запуск по пути к директории
pytest tests/e2e/ -v
```

## Полезные команды и фичи Pytest

### Автоматическая разметка слоев (Auto-Applied Markers)
В наборе тестов используется кастомный хук коллекционирования в `tests/conftest.py`, который автоматически размечает тесты на основе их расположения в директориях:
* Тесты внутри `tests/unit/` автоматически получают маркер `@pytest.mark.unit`
* Тесты внутри `tests/integration/` получают маркер `@pytest.mark.integration`
* Тесты внутри `tests/e2e/` получают маркер `@pytest.mark.e2e`

Благодаря этому вам **не нужно** вручную прописывать декораторы `@pytest.mark.*` в новые файлы тестов!

### Комбинирование маркеров
Вы можете запускать несколько слоев одновременно, используя стандартную логику:

```bash
# Запуск одновременно unit и integration тестов (удобно для быстрой локальной проверки перед коммитом)
pytest -m "unit or integration"
```

### Полезные флаги CLI

* `-v` : Подробный (verbose) вывод.
* `-x` : Остановить выполнение при первой же ошибке.
* `--lf` : Перезапустить только тесты, которые упали в прошлый раз (last failed).
* `-s` : Отключить перехват стандартного вывода (позволяет видеть вывод от функций `print()`).
* `-k <имя>` : Фильтрация тестов по подстроке в их названии (например, `pytest -k test_auth`).
