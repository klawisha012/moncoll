# Нагрузочное тестирование WAF с использованием wrk

В этой директории находятся скрипты для проведения высокопроизводительного нагрузочного тестирования WAF с помощью утилиты [wrk](https://github.com/wg/wrk).

Мы перешли с **k6** на **wrk**, чтобы обеспечить максимальную производительность тестов и задействовать **все доступные ядра процессора**.

---

## Почему именно wrk?

1. **Многопоточность и масштабируемость**: В отличие от k6, который может упираться в производительность однопоточного JavaScript-движка в контейнере, `wrk` написан на языке C и использует нативную многопоточность (`epoll` / `kqueue`). Он может задействовать абсолютно все ядра процессора для генерации экстремальных нагрузок.
2. **Экстремально низкие накладные расходы**: `wrk` способен генерировать сотни тысяч запросов в секунду (RPS) с минимальным потреблением CPU и оперативной памяти на стороне генератора, что гарантирует чистоту результатов (вы тестируете именно накладные расходы WAF, а не возможности нагрузочного агента).
3. **Lua-скрипты**: Скрипты на Lua позволяют гибко манипулировать запросами (динамически подставлять заголовки, генерировать случайные IP-адреса для обхода блокировок и передавать различные POST-тела) на максимальной скорости.

---

## Основные параметры wrk (Использование всех ядер)

Для полной утилизации вашего процессора всегда настраивайте параметр потоков (`-t` или `--threads`):

* `-t, --threads` : Количество потоков. **Всегда устанавливайте равным числу ядер (или логических процессоров) вашего CPU!** (в вашей текущей системе обнаружено **32 логических процессора**, поэтому рекомендуется выставлять `-t 32`).
* `-c, --connections` : Общее число удерживаемых одновременно HTTP-соединений. **Оно обязательно должно быть больше или равно количеству потоков (`-c >= -t`)**, иначе `wrk` завершится с ошибкой `number of connections must be >= threads` (например, для 32 потоков используйте минимум `-c 32`, а лучше `-c 128` или `-c 400`).
* `-d, --duration` : Длительность теста (например, `-d 30s` или `-d 5m`).
* `-s, --script` : Путь к Lua-скрипту для кастомизации запросов.

---

## Сценарии тестирования (Lua-скрипты)

Мы подготовили 4 сценария в папке `tests/loadtest/wrk/`:

1. **`smoke.lua`**: Быстрый дымовой тест. Делает базовые GET-запросы на `/` без изменения заголовков. Применяется для базовой проверки доступности.
2. **`random_ips.lua`**: Симуляция множества уникальных клиентов. Генерирует случайные IP-адреса в заголовках `X-Forwarded-For` и `X-Real-IP`, позволяя обойти ограничители (rate-limiters) и протестировать корректность маршрутизации WAF.
3. **`compression.lua`**: Тестирование матрицы сжатия. Поочередно запрашивает разные кодировки (`zstd`, `br`, `gzip`, `identity`), позволяя оценить нагрузку на CPU от сжатия «на лету» в Angie.
4. **`post_attack.lua`**: Имитация вредоносного трафика. Шлет POST-запросы со смесью легитимных параметров и WAF-атак (SQLi, XSS, Path Traversal), заставляя парсер ModSecurity анализировать тела запросов и вычислять регулярные выражения. Это лучший тест для замера максимальных накладных расходов правил WAF.

## Запуск тестов локально (через Docker Compose)

Сервис `wrk` вынесен в профиль `loadtest`, поэтому он не запускается по умолчанию со всем стеком. Утилита запускается явно.

> [!TIP]
> Примеры ниже автоматически преднастроены под вашу 32-поточную систему (`-t 32 -c 128`). Вы можете уменьшать или увеличивать эти значения в зависимости от характера теста.

### 1. Дымовой тест (Smoke)
Быстрая проверка доступности WAF (10 секунд, 128 соединений):
```bash
docker compose --profile loadtest run --rm wrk -t 32 -c 128 -d 10s -s /scripts/smoke.lua http://angie/
```

### 2. Тестирование с рандомизацией IP (Стресс-тест маршрутизации)
Имитация 10 000 клиентов из разных подсетей для проверки WAF и CrowdSec под нагрузкой:
```bash
docker compose --profile loadtest run --rm wrk -t 32 -c 1000 -d 60s -s /scripts/random_ips.lua http://angie/
```

### 3. Тест накладных расходов WAF под атаками (ModSecurity)
Замеры производительности парсера правил ModSecurity под смесью легитимных и вредоносных POST-запросов:
```bash
docker compose --profile loadtest run --rm wrk -t 32 -c 200 -d 30s -s /scripts/post_attack.lua http://angie/
```

### 4. Тестирование производительности сжатия
Проверка влияния алгоритмов сжатия (zstd / brotli / gzip) на задержки и CPU-ресурсы:
```bash
docker compose --profile loadtest run --rm wrk -t 32 -c 200 -d 45s -s /scripts/compression.lua http://angie/
```

## Анализ результатов wrk

После завершения теста `wrk` выведет отчет следующего вида:

```text
Running 30s test @ http://angie/
  32 threads and 128 connections
  Thread Stats   Avg      Stdev     Max   +/- Stdev
    Latency     8.45ms    3.12ms  42.12ms   78.41%
    Req/Sec     4.12k   412.31     5.82k    72.10%
  1478120 requests in 30.01s, 1.12GB read
Requests/sec:  49254.21
Transfer/sec:    38.21MB
```

### На что обращать внимание:
* **Latency (Задержка)**: Среднее время ответа (Avg) и максимальное (Max). При включенном ModSecurity с тяжелыми наборами правил (OWASP CRS) средняя задержка на горячем пути может возрастать — используйте `post_attack.lua` для замера этой дельты.
* **Requests/sec (RPS)**: Общее количество обрабатываемых запросов в секунду. Это главный показатель пропускной способности WAF.
* **Socket errors**: Если в конце отчета появляются строки с ошибками (Read, Write, Timeout), это сигнализирует о том, что WAF захлебывается (исчерпан лимит файловых дескрипторов `ulimit -n`, переполнен стек TCP-соединений `net.core.somaxconn` или буферы проксирования).
